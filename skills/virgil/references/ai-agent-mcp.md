# AI Agent, LLM, Tooling (MCP) & Runtime Safety

## 1. Threat Taxonomies (OWASP LLM 2025, Agentic Top 10 2026, MITRE ATLAS, NIST)
- `[YELLOW]` **Unmapped Trust Boundaries & Evaluation Gates:** Map agent tools, memory stores, and connectors against **OWASP Top 10 for LLM Applications (2025)** (`LLM01–LLM10`), **OWASP Top 10 for Agentic Applications (2026)** (`ASI01–ASI10`), **MITRE ATLAS** (`AML.T0051`, `AML.T0053`, `AML.T0057`), and **NIST AI RMF 1.0 / AI 600-1**. Enforce architectural controls and CI adversarial evaluations (never rely on model refusals alone).

## 2. Prompt Injection & Trust Boundaries (`LLM01:2025`, `AML.T0051`)
- `[RED]` **Untrusted External Data Reaching Privileged Tool Loops & "Rule of Two":** Never pass raw external content (web pages, emails, GitHub issues/PRs, PDFs, tool returns, RAG chunks) into an LLM loop holding state-mutating, network, or code-exec tools without architectural separation. Follow the **Rule of Two**: never let a single agent context combine (1) private/sensitive data, (2) untrusted external inputs, and (3) external state mutation/exfiltration without deterministic HITL or IFC gating.
  - Apply **Dual-LLM (P-LLM / Q-LLM)** or **CaMeL Information Flow Control (IFC)**: isolate untrusted parsing in a zero-tool Quarantined LLM returning strict typed schemas (enums/booleans/numbers), and enforce deterministic provenance/capability checks before any untrusted data influences control flow or sink arguments (URLs, recipients, shell commands).
- `[RED]` **Inter-Agent Trust Exploitation (`ASI07`) & Browser Isolation:** Treat every sub-agent, peer-agent, and orchestrator handoff as an untrusted trust boundary (validate schemas and permissions on every hop; never treat peer-agent output as privileged instructions). Run browser/computer-use agents strictly inside disposable, isolated browser containers with zero access to host profiles or credentials.
- `[YELLOW]` **Weak Channel Separation:** Separate `system`/`developer`, `user`, and `tool` channels structurally, delimit untrusted tool payloads, and strip zero-width Unicode and ANSI escape sequences at ingestion.

## 3. Tool, Plugin & MCP (Model Context Protocol) Security (`ASI02`–`ASI04`)
- `[RED]` **Excessive Agency & Unvalidated Tool Arguments (`LLM06:2025`, `ASI02`):** Replace generic `run_shell`, `execute_sql`, or unrestricted `http_request` tools with narrow, typed task tools. Partition into Tier 1 (read-only internal), Tier 2 (scoped local reversible), and Tier 3 (irreversible/external: delete, send email, deploy, transfer funds, install packages). Mandate deterministic out-of-band **HITL approval** showing exact resolved args on Tier 3. Validate all tool arguments outside the LLM via strict JSON Schema (`additionalProperties: false`), `realpath` workspace containment (`CWE-22`), `execFile` binary allowlists (`CWE-78`), and domain allowlists blocking private/metadata IPs (`CWE-918`).
- `[RED]` **MCP Token Passthrough & Confused Deputy (`ASI03`):** Implement **OAuth 2.1 + PKCE (`S256`)**, **RFC 9728** (`/.well-known/oauth-protected-resource`), and **RFC 8707** (`resource` binding). MCP servers MUST verify exact matching `aud` claims and NEVER pass incoming tokens through blindly downstream. MCP proxies MUST isolate consent/tokens per user session (mid-2026 MCP spec deprecates Dynamic Client Registration in favor of pre-registration / Client ID Metadata Documents).
- `[RED]` / `[YELLOW]` **MCP Tool Poisoning ("Line Jumping"), Rug Pulls & Shadowing (`ASI04`):** Pin MCP tool manifests by cryptographic hash to detect post-TOFU schema/description mutations (`[RED]` if untrusted dynamic manifests auto-execute), strip ANSI/control chars from descriptions, and never attach untrusted + high-privilege MCP servers to the same active agent context (`[YELLOW]` / `[RED]` depending on privilege).

## 4. Execution Sandboxing & Credential Isolation (`ASI05`)
- `[RED]` **Host Breakout, `--dangerously-skip-permissions` & Env Secret Exposure (`CWE-78`, `AML.T0025`):** Isolate untrusted/multi-tenant execution in **Firecracker microVMs** or **gVisor (`runsc`)**; for local dev sandboxes, enforce OS primitives (`bubblewrap` namespaces + `socat` on Linux/WSL2; macOS Seatbelt `sandbox-exec`), mounting only the target workspace read-write and explicitly blocking reads to `~/.ssh`, `~/.aws`, `~/.gnupg`, and keychains. Never mount `/var/run/docker.sock`.
- `[RED]` **Direct Egress or Raw Keys in Sandbox `env`:** Disable direct outbound networking inside the sandbox (`--unshare-net` / `vsock`), route HTTP/HTTPS through a host-side allowlisting **egress proxy** blocking RFC 1918 and `169.254.0.0/16`, and inject `Authorization` headers strictly at the proxy so raw API/Git/cloud keys never enter sandbox environment variables or files.

## 5. RAG, Persistent Memory, PII & Downstream Output Safety
- `[RED]` **Cross-Tenant RAG Leakage & Poisoning (`LLM08`, `LLM04`, `ASI06`, `CWE-862`):** Enforce **pre-retrieval metadata/ACL filtering** (`tenant_id`, `role`, provenance) inside the vector DB query itself—never filter sensitive documents in the prompt after retrieval. Isolate tenant namespaces, strip hidden document text before embedding, and require provenance/TTL integrity on persistent agent memory.
- `[RED]` **PII / Secret Transmission & Untrusted Output Handling (`LLM02`, `LLM05:2025`):** Run deterministic DLP/regex redaction hooks (`PreToolUse` / egress filter) to strip `.env` files, keys, and PII prior to external model calls. Treat all LLM output as untrusted input at downstream sinks: sanitize Markdown/HTML (disable raw HTML, `javascript:`/`data:` URLs, and external tracking `<img>` beacons), parameterize SQL, ban shell interpolation, and canonicalize paths.
- `[YELLOW]` **LLM Provider Data Retention & DSR Propagation (Google SAIF / Privacy):** Verify zero-data-retention (ZDR) and training opt-out contracts/settings before sending regulated customer data to external LLM APIs, and ensure user erasure (DSR) deletes associated chunks from RAG vector stores and persistent agent memory.

## 6. Agent-Generated Code Risks, Verification Loops & Runtime Caps
- `[RED]` **Empirical LLM Code Traps & Slopsquatting (`CWE-798`, `CWE-89`, `CWE-295`, `CWE-862`, `CWE-942`):** Explicitly audit agent-generated code for hardcoded fallback secrets, disabled TLS verification (`verify=False`, `NODE_TLS_REJECT_UNAUTHORIZED=0`), permissive CORS (`*` + credentials), missing authz, and **hallucinated package names** (autonomous `pip`/`npm` installs without registry verification and lockfile pinning).
- `[YELLOW]` **Missing Verification Gates, Audit Trails & Kill Switches (`LLM10:2025`, `ASI08`, `ASI10`):** Gate agent PRs with SAST (Semgrep/CodeQL), secret scanning, and dependency gates. Emit structured OTel/JSON audit logs (`session_id`, `principal`, `tool_name`, sanitized args, `policy_decision`) to off-sandbox WORM storage. Enforce hard turn/step limits, per-session/tenant spend caps, retry-loop circuit breakers, and instant out-of-band kill switches.

## Verification Checklist
- Trace untrusted inputs (`web`, `email`, `PR`, `RAG`, `MCP`) to prove zero direct path to mutating/exec tools without schema/IFC/HITL gates.
- Test MCP OAuth servers with wrong-audience tokens, mutate a tool manifest to verify hash-pinning blocks execution, and test sandbox `printenv`, `~/.ssh` reads, and `169.254.169.254` egress failure.
- Execute cross-role RAG queries, synthetic LLM XSS/Markdown exfil beacons, and runaway loop budget tests.
